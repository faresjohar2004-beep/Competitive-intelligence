WHAT ASTRA OS ACTUALLY IS
A daily habit/identity-change app (web + native mobile, Clerk-gated) built around a promise→action→evidence→score→streak core loop, wrapped in an AI coach, AI-written future-self letters, an AI-generated daily biography, and an unlockable chapter system. Positioned explicitly as "an OS for identity change," not a task manager (Landing.tsx:253,259).

CURRENT USER JOURNEY
Landing page → 3-question guest onboarding → Clerk signup with auto-resumed answers → pre-seeded Dashboard → daily loop of promise/action/reflect, with secondary nav into Missions, Life Scores, Letters, Biography, Timeline, Hall of Regret. Mobile mirrors this across 5 tabs.

STRONGEST FEATURES
1. Core promise/action/evidence/score loop — fully real, cross-verified.
2. Account deletion — robust Stripe+Clerk+DB purge with idempotent cron retry.
3. AI coach context injection — genuinely live-assembled, the strongest true "AI" claim in the product.

WEAKEST FEATURES
1. Settings "Save Changes" — fully decorative, name field hardcoded, label unlinked.
2. Life Map history — dead table, dead endpoint, Math.random()-filled.
3. Backend input validation — systemically absent across every route despite ready-made schemas.

FUNCTIONAL VS PARTIAL FEATURES
Functional: Dashboard, Actions, Missions, Future Self scores, Chapters, Biography, Coach, Evidence Vault, Reflections, Share, Stripe billing, Account Deletion, Push Notifications, Promise Streak, all 5 mobile tabs.
Partial/fabricated: Settings (dead save), Life Map history (random+orphaned), Future Self "AI Projection" (deterministic, mislabeled), Timeline (hardcoded offsets, mislabeled), Letters (random tone; fake-dated teaser when 0 real letters), initial Life/Future-Self score seeding (random, new finding), Landing + Dashboard fabricated statistics.

BIGGEST UX FRICTION
Two confirmed broken links firing right after positive-reinforcement moments (Reflections → /future, Dashboard → /trajectory, both 404), compounded by zero user-facing feedback on failed core-loop mutations on both web and mobile.

BIGGEST RETENTION RISK
The mobile promise-reconciliation bug's root cause is now proven at the code level (missing cache invalidation in useMissions.ts:44-46), and a second instance of the exact same bug was found this week on the Actions tab — so a user can now see stale/contradictory state across the promise card AND their streak/score, not just one element.

BIGGEST COMMODITY RISK
Score 62/100, unchanged. Streaks/check-ins/AI chat are category-standard; the identity-narrative moat is only partly genuine and cannot be measured, since no analytics/telemetry infrastructure exists anywhere in the codebase.

STRONGEST DIFFERENTIATOR
The AI coach's real-time context injection, plus the Hall of Regret/Courage Challenge loss-aversion mechanics — real, computed, uncommon in commodity habit trackers.

WEAKEST DIFFERENTIATOR
The "AI Projection" of your future self is a deterministic arithmetic formula with no model call (ai.ts:353-383), compounded by fabricated statistics on both the landing page and inside the authenticated app, and — new this week — a randomized rather than onboarding-derived initial score baseline.

IDENTITY SYSTEM ASSESSMENT — 72/100
Genuinely load-bearing (real identity statements, Evidence Vault, AI letters/biography grounded in real activity), undermined by fabricated onboarding defaults and a fully dead profile-photo pipeline (Clerk avatar captured, never rendered; expo-image-picker dependency unused end-to-end).

FAILURE RECOVERY ASSESSMENT — 55/100
Excellent for account deletion; weak for the highest-frequency actions. New this week: mobile's missions.tsx handleComplete swallows errors with console.error only, confirming the same error-handling gap previously documented only on web now also exists on mobile.

TOP 5 PRODUCT PROBLEMS
1. The mobile cache-invalidation bug is now proven and shown to be broader than previously known — it affects streak/score display, not just the promise card.
2. Backend input validation is systemically absent across every route despite ready-made validation schemas already existing for every table.
3. Fabricated statistics persist on the landing page, inside the authenticated Dashboard, and now confirmed to extend to the user's very first onboarding-derived score baseline.

5. Multiple screens present formulaic or random output as real personalized/predictive data (Life Map history, Future Self projection, Timeline, Letters tone, initial score seeding).

TOP 5 PRODUCT OPPORTUNITIES
1. Add getGetMeQueryKey/getGetTodayActionsQueryKey invalidation to useMissions.ts's onSuccess, and the equivalent stat/future-self keys to actions.tsx's logAction — both are small, now-proven, targeted fixes for the same bug class.
2. Wire up .safeParse() against the already-existing drizzle-zod schemas on the highest-traffic routes (actions.ts, missions.ts) first — the schemas are already written, this is purely wiring.
3. Extend the error-handling pattern that already works elsewhere (Dashboard Quick Log, Reflections) to Actions.tsx/Missions.tsx (web) and missions.tsx's handleComplete (mobile) — proven, reusable infrastructure, not new work.
4. Replace the two random-seeding fabrications (initial Life/Future-Self scores, Life Map history) with the real computations the schema already supports.
5. Regenerate the OpenAPI spec from current routes, prioritizing the account-deletion endpoint and the four entirely undocumented route files.
